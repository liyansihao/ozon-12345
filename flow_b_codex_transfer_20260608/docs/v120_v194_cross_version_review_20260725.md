## 1. 统一事实集

统一口径：

- 候选：窗口内 collection attempts 与 candidate/stage/selected 唯一 SKU 并集的较大值。
- pure FBS：真实详情确认后进入利润上限计算的唯一 SKU。
- 可靠成本：得到可靠 1688 成本并进入利润计算的唯一 SKU。
- 利润通过：窗口内 selected 且利润率严格大于 30% 的唯一 SKU。
- 提交：进入 Maozi 发布与最终确认阶段的唯一 SKU。
- 窗口确认：确认时间位于窗口内，ERP/Ozon 状态 selling、库存大于 0 的唯一 SKU。
- 迟到确认：本版本窗口内选择，但窗口结束后才首次严格确认的 SKU。
- 含迟到生产速度按“本版本自产窗口确认 + 本版本选择后的迟到确认”归因，不把前序积压算成本版本产能。

从综合最佳 v139 commit 到当前 v194 commit 的 tracked diff 为 63 个文件：

- 4 个测试文件；
- 4 个生产源码文件；
- 总计新增 2266 行、删除 21 行。

4 个生产源码文件相对 v139 仅净增 24 行：

- `flow_b_acceptance_preflight.mjs`：仓库映射，净 0 行；
- `flow_b_playwright.mjs`：仓库映射和短窗报告，净 0 行；
- `continuous-runtime.mjs`：短窗报告，+10 行；
- `source-scanner.mjs`：三轮 dry-rotation 改写，+14 行。

因此“约 120 个文件变化”绝大多数是运行证据，不是 120 个源码修改。真正需要从 v139
带入的新生产源码职责只有两个：仓库映射正确性和短窗报告正确性，涉及 3 个生产源码文件；
`source-scanner.mjs` 的后续 +14 行没有跨版本最终速度收益证据，先舍弃。

当前代码确实比 v139 更复杂但效果更差，不过复杂度增量主要集中在 source scanner 的 dry-rotation
分支和大量实验配置，而不是整个项目被重写。性能下降的主因是候选来源持续耗尽和配置漂移，
不是 24 行代码本身的执行开销。
